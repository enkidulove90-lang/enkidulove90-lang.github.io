> 论文：[arXiv 2507.21892](https://arxiv.org/abs/2507.21892) · 代码：[GitHub](https://github.com/LHRLAB/Graph-R1)

"把知识组织成图"这件事，在 RAG 里看起来天经地义：文本块检索丢了结构语义，那就把文档抽成实体关系图，检索时沿着图走。但真做起来有个尴尬的结果——**图结构本身并不会自动带来收益**。

论文用一组对比直接点破了这一点。在 2WikiMultiHopQA 上，用 GPT-4o-mini 做纯提示的场景里：

| 方法 | F1 |
|---|---|
| StandardRAG（文本块检索） | **22.31** |
| HyperGraphRAG | 21.14 |
| GraphRAG | 16.02 |
| LightRAG | 16.59 |
| PathRAG | 12.42 |

也就是说，几个主流 GraphRAG 变体的 F1 都**低于**不做图、只做文本块检索的 StandardRAG。问题不在图，而在**怎么用图**：这些方法都是"一次性检索 + 拼进提示"，图只是换了一种取文档的方式，模型并没有真正"在图上推理"。

Graph-R1 的答案是：把图检索变成**多轮智能体交互**，并用**端到端强化学习**训练这套交互策略。

![Graph-R1 把 GraphRAG 建模为知识超图上的多轮智能体检索过程，用端到端强化学习优化](images/graphr1-teaser.jpg)

## 一、方法：知识超图 + 结构化动作空间 + GRPO

![Graph-R1 框架：强化学习增强的推理轨迹，智能体迭代地思考、查询图环境、并作答](images/graphr1-framework.jpg)

如上图，整条链路有三段：**知识构建 → 多轮图交互 → 结果导向的端到端强化学习**。

### 1. 知识超图：比普通图更贴近"多跳事实"

论文没有用普通三元组图，而是构建**知识超图（knowledge hypergraph）**：

```text
G_H = (V, E_H, φ)
π_ext(d) → { (h_i, V_{h_i}) }_{i=1..m}
```

即从每个文本块 `d` 中抽取事实时，允许**一条超边连接多个节点**（`V_{h_i}` 是一个集合），而不是只能两两相连。原因是多跳问答里大量事实天然是 n 元的——"某奖项由某机构在某年颁给某作品"这类陈述，硬拆成二元组会丢信息。

超图的抽取用 GPT-4o-mini 完成，检索侧的向量模型统一用 `bge-large-en-v1.5`。

### 2. 多轮交互：把推理拆成可训练的动作

每一步 `t`，智能体生成一个**结构化输出**，包含三部分：

```text
π_θ( a_t^think , α_t , a_t^out | s_t )
```

- `a_t^think`：思考/反思（当前已知什么、还缺什么）
- `α_t`：**动作选择**——在动作空间里选一个（从图环境查询、检索、作答…）
- `a_t^out`：本步输出的内容

关键在于 `α_t` 让"查什么"变成**可学习的离散决策**。图在这里不是"取文档的工具"，而是一个可以被反复访问的**环境**：智能体可以查一次、看到结果、再决定要不要沿另一条边继续查。这才是"在图上推理"与"用图取文档"的区别。

### 3. 训练：只给结果打分

优化目标用的是 **GRPO（Group Relative Policy Optimization）**：

```text
J_GRPO(θ) = E[ ... ]      每个问题采样一组轨迹，用组内相对优势更新策略
```

设计上值得注意的一点是**结果导向（outcome-directed）**：奖励只来自最终答案的正确性（EM/F1 这类），**不对中间步骤做显式监督**。理由是多跳问答的中间步骤没有可靠标注，强行监督反而会引入错误引导；而用组内相对比较（同一问题的多条轨迹互相比），可以在没有步骤标注的情况下得到稳定的梯度信号。

一个容易被忽略的工程细节：知识构建与检索生成是**分开算成本**的。Graph-R1 的检索阶段成本记为 **0 美元**（表 3），因为检索发生在自建的超图环境里，不需要调用外部 API——这与依赖商业 API 做检索的 GraphRAG 变体形成直接对比。

## 二、实验

### 设置

六个标准 RAG 数据集：2WikiMultiHopQA、HotpotQA、Musique、NQ、PopQA、TriviaQA。四个指标：EM、F1、R-S（检索相似度）、G-E（生成评测）。主干模型覆盖 **Qwen2.5 的 1.5B / 3B / 7B** 三档。

基线包括：NaiveGeneration、StandardRAG、SFT、R1、Search-R1、R1-Searcher，以及 GPT-4o-mini 驱动的各 GraphRAG 变体（GraphRAG、LightRAG、PathRAG、HippoRAG2、HyperGraphRAG）。

### 主结果：随基座增大稳定拉开差距

| 主干 | 方法 | 平均 EM | 平均 F1 |
|---|---|---|---|
| Qwen2.5-1.5B | Search-R1 | 23.18 | 29.53 |
| Qwen2.5-1.5B | R1-Searcher | 23.70 | 32.26 |
| Qwen2.5-1.5B | **Graph-R1** | **31.90** | **40.09** |
| Qwen2.5-3B | Search-R1 | 28.65 | 35.69 |
| Qwen2.5-3B | R1-Searcher | 27.08 | 34.91 |
| Qwen2.5-3B | **Graph-R1** | **42.45** | **51.26** |
| Qwen2.5-7B | Search-R1 | 38.54 | 46.19 |
| Qwen2.5-7B | R1-Searcher | 34.51 | 42.29 |
| Qwen2.5-7B | **Graph-R1** | **48.57** | **57.82** |

两个观察值得摘出来：

**① 强化学习才让图表示"活"起来。** 纯提示的 GraphRAG 变体普遍不如 StandardRAG（开头那张表），而 Graph-R1 靠多轮交互 + RL 把同一份图结构用出了完全不同的效果。**结论是"图的价值取决于使用方式"，而不是"图本身有没有价值"。**

**② 基座越大，优势越大。** 三档参数下 F1 分别是 40.09 / 51.26 / 57.82，与次优基线的差距同步扩大。这说明该框架吃的是"策略学习能力"，模型越强越能把它用好。

单数据集上差距更直观（7B）：

| 数据集 | Search-R1 F1 | Graph-R1 F1 |
|---|---|---|
| 2WikiMultiHopQA | 41.29 | **65.04** |
| HotpotQA | 50.85 | **62.69** |
| Musique | 22.35 | **46.17** |
| NQ | 45.88 | **49.87** |
| PopQA | 50.76 | **51.22** |
| TriviaQA | 65.98 | **71.93** |

**多跳数据集（2Wiki、Musique）上的差距最大**——2Wiki 上 F1 从 41.29 提到 65.04，Musique 从 22.35 到 46.17。这与设计意图完全吻合：**需要跨多条边串起事实的任务，才是图结构真正能发挥作用的地方**；单跳事实问答上优势就小得多（PopQA 只从 50.76 到 51.22）。

![跨 RAG 基准的 F1 对比：以图为知识环境让强化学习获得更高的性能上限](images/graphr1-f1.jpg)

### 消融：三个组件里 RL 最不能少

| 变体（Qwen2.5-7B） | 平均 EM | 平均 F1 | G-E |
|---|---|---|---|
| Graph-R1 | 56.25 | 63.87 | 81.23 |
| 去掉知识构建（w/o K.C.） | 46.68 | 53.87 | 76.34 |
| 去掉多轮交互（w/o M.I.） | 39.07 | 45.91 | 69.81 |
| **去掉强化学习（w/o R.L.）** | **1.56** | **17.79** | 77.37 |

这张表里最刺眼的是最后一行：**去掉 RL 后，平均 EM 掉到 1.56、F1 掉到 17.79**——模型基本不会用了，几乎退化为随机输出。3B 档同样（EM 3.13 / F1 10.74）。

一个非常有价值的细节：**w/o R.L. 的 G-E 仍有 77.37**，与完整模型的 81.23 相差不大。也就是说，**去掉 RL 之后，生成的文字看起来依然顺畅、格式依然像样，但答案基本是错的**。如果只靠"读起来像不像"来判断，这个崩塌会被完全掩盖——这对所有做生成式 agent 评测的人都是一个提醒：**生成质量指标不能替代任务正确性指标**。

三个组件的相对重要性也很清楚：RL（不可替代）> 多轮交互 > 知识构建。

### 成本与效率

| 方法 | 知识构建 | 图规模（节点/边） | 检索+生成 | F1 |
|---|---|---|---|---|
| NaiveGeneration | 0 s / 0 $ | — | 3.7 s / 0.16 $ | 17.0 |
| StandardRAG | 0 s / 0 $ | — | 4.1 s / 1.35 $ | 22.3 |
| GraphRAG | 8.04 s / 3.35 $ | 7,771 / 4,863 | 7.4 s / 3.97 $ | 16.0 |
| LightRAG | 6.84 s / 4.07 $ | 59,197 / 24,596 | 12.2 s / 8.11 $ | 16.6 |
| PathRAG | 6.84 s / 4.07 $ | 59,197 / 24,596 | 15.8 s / 8.28 $ | 12.4 |
| HippoRAG2 | 3.25 s / 1.26 $ | 11,819 / 40,654 | 8.8 s / 7.68 $ | 16.3 |
| HyperGraphRAG | 6.76 s / 4.14 $ | 173,575 / 114,426 | 9.6 s / 8.76 $ | 21.1 |
| **Graph-R1 (7B)** | 5.69 s / 2.81 $ | 120,499 / 98,073 | 7.0 s / **0 $** | **65.0** |

（成本按 GPT-4o-mini 计价；检索阶段 0 美元是因为查询发生在自建超图环境内，不调用外部 API。）

两个结论：**一是知识构建成本与图规模并不决定效果**（HyperGraphRAG 建了 17 万节点，F1 只有 21.1）；**二是把成本从"每次查询付费"转移到"一次构建 + 本地检索"**，使单次查询的边际成本变成 0——这在生产环境里比峰值精度更有吸引力。

## 三、总结

Graph-R1 的核心主张可以浓缩成一句：**图的价值取决于使用方式，而使用方式本身是可以被强化学习学出来的。**

四个可迁移的判断：

1. **"用了图"不等于"用好了图"**：纯提示的 GraphRAG 变体在多跳数据上会输给朴素文本检索——把图塞进提示，和让模型在图上多轮探索，是两件事。
2. **让"查什么"变成可微的决策**：把动作空间显式建模（查询图 / 检索 / 作答），才谈得上训练策略。
3. **结果导向的 RL 足以驱动多步推理**：只看最终答案正确性、不做步骤监督，即可训练多轮检索；GRPO 的组内相对比较是关键抓手。
4. **警惕"看起来正常"的评测假象**：去掉 RL 后生成质量指标仅从 81.23 降到 77.37，但任务指标从 63.87 崩到 17.79——**评测必须绑定任务正确性**。
