DSpark：用半自回归草稿与置信度调度，把推测解码的验证预算花在刀刃上

发表于2026-07-06|更新于2026-10-25|推荐系统论文速递
|总字数:4.3k|阅读时长:14分钟|浏览量:

论文：arXiv 2607.05147 · 代码：GitHub · PDF：本地阅读

大模型推理的延迟本质上由自回归解码决定：每生成一个 token 都要完整前向一次，输出越长，用户等待越久。推测解码把“草稿”和“验证”拆开，用轻量草稿模型一次提出多个候选 token，再由目标模型并行验证，按拒绝采样接受最长一致前缀，从而在不改变目标分布的前提下加速生成。这条路线在实时对话、多轮 Agent 等延迟敏感场景中已经成为生产系统的标配组件。

但草稿模型的设计长期存在一个两难。自回归草稿器逐 token 生成，能建模 token 间依赖，接受率高，可草稿延迟随块大小线性增长，只能使用短块和浅层网络；并行草稿器一次前向产出整块候选，草稿延迟几乎与块大小无关，却因为每个位置独立预测而丢失块内依赖，越靠后的位置接受率衰减越快。DSpark 的出发点正是承认这两类结构各有不可替代的优势，而不是在其中选边。

论文的另一个观察来自系统侧：即便草稿块很长，把所有候选 token 都送去验证也未必划算。结构化任务（如代码）天然接受率高，开放聊天接受率低；轻负载下多验证几个 token 几乎无代价，高并发下每一个注定被拒绝的 token 都在占用目标模型的批处理容量。也就是说，验证长度不应是固定超参数，而应随请求难度和引擎负载动态变化。

DSpark 因此由两个互补机制组成：半自回归生成，用并行骨干承担主要草稿计算、只附加轻量串行头注入块内依赖；置信度调度验证，用置信度头估计前缀存活概率，再由硬件感知调度器按实时吞吐曲线为每个请求分配验证预算。前者改善“草稿得多准”，后者改善“验证得多值”。

需要提前说明部署条件：离线实验在 Qwen3-4B/8B/14B 与 Gemma4-12B 上进行，块大小 γ=7，所有草稿器在同一训练框架、同一数据上重训；在线结果来自 DeepSeek-V4-Flash 与 V4-Pro 生产服务引擎的真实用户流量，基线是生产配置 MTP-1。硬件型号、软件框架版本与训练超参数（学习率、优化器等）原文未披露，因此复现时这些条件需要自行补齐。

一、方法：半自回归草稿与置信度调度验证

DSpark 的优化目标可以直接从每 token 延迟公式读出：L = (T_draft + T_verify) / τ。降低草稿时间、提高接受长度 τ、或减少有效验证时间，是仅有的三个杠杆。半自回归结构同时作用于前两项，置信度调度作用于第三项。

这张图应按从左到右的解码时序阅读。左侧提示 token ABC 经目标模型一步前向得到锚点 D；D 作为草稿阶段输入，进入“重”并行骨干与“轻”串行头，产出草稿 token EFGH 及对应置信度分数；随后硬件感知前缀调度器根据这些分数保留前缀 EFG、丢弃低置信的 H；最后目标模型并行验证被调度的前缀，E、F 被接受，G 被拒绝并由目标模型给出修正 token G*，完成本轮。它支撑的核心主张是：草稿阶段可以又并行又带块内依赖，而验证阶段不必照单全收。

1.1 并行骨干加轻量串行头

并行阶段沿用 DFlash 作为骨干，一次前向产出整块的隐藏状态 h_1…h_γ 与基础 logits U_1…U_γ。DSpark 对骨干只做了一处小改动：把锚点本身当作第一个预测位置，于是 γ 个输入 token（锚点加 γ−1 个 mask）直接产出 γ 个草稿 logits，减少了一次草稿计算。

串行阶段不重新定义全局归一化的能量模型，而是通过自回归分解引入前缀相关偏置 B_k：第 k 位的草稿分布等于 softmax(U_k + B_k)，其中 B_k 依赖锚点 x_0 与块内已采样前缀 x_<k。推理时从左到右采样，因此串行块必须足够轻，使整体草稿延迟仍由并行阶段主导。论文给出两种实例化：Markov 头把 B 限制为一阶转移，并用低秩分解 B = W_1 W_2（默认秩 r=256）近似 V×V 转移矩阵，W_1 充当嵌入查表、W_2 充当 logit 投影；RNN 头则维护循环状态 s_k，把上一状态、上一 token 嵌入与骨干隐藏 h_k 拼接后做一次门控更新，从而访问整个块内前缀。

这一设计直接针对并行草稿的“多模态碰撞”：当上下文同时允许“of course”和“no problem”时，独立预测可能拼出“of problem”。一旦第 1 位采样到“of”，Markov 头会抬高“course”并压低“problem”，把后缀拉回同一语义路径。

1.2 置信度头与顺序温度缩放

置信度头对每个草稿位置输出标量 c_k ∈ (0,1)，含义是“在前缀全部被接受的前提下，第 k 位 token 能通过目标验证”的条件概率。结构很轻：把骨干隐藏 h_k 与上一 token 的 Markov 嵌入拼接后做线性投影加 sigmoid。监督信号是解析接受率 c_k* = 1 − ½‖p_k^d − p_k^t‖_1，即草稿分布与目标分布的总变差距离的补。

仅有排序能力还不够。阈值式方法只需要置信度能正确排序草稿质量，而调度器要计算期望接受长度 τ，必须让累积存活概率的绝对幅度可信。神经置信度估计通常过度自信，因此 DSpark 引入顺序温度缩放：利用留出验证集，从左到右逐位置做一维网格搜索，在固定已校准前缀分数的前提下最小化累积乘积的期望校准误差。温度缩放是保序变换，校准概率幅度的同时不破坏置信度头学到的相对排序。

1.3 硬件感知前缀调度器

调度问题被写成全局吞吐最大化。对 R 个活跃请求，第 r 个请求第 j 位的存活概率是累积乘积 a_{r,j} = ∏_{i≤j} c_{r,i}；一次验证送给目标模型的批大小为 B = Σ(1+ℓ_r)，期望接受 token 数为 τ = Σ(1+Σ a_{r,j})；引擎吞吐 SPS(B) 在初始化时剖析一次并存成轻量代价表。目标是最大化 Θ = τ · SPS(B)。

由于 a_{r,j} 随 j 单调不增，把请求 r 的验证长度从 j−1 延到 j 的边际收益恰好是 a_{r,j}。算法把所有候选前缀扩展按存活概率全局降序排列，逐个接纳并查表更新 Θ，一旦吞吐下降就立即停止。这个提前停止还有因果性上的必要性：置信度头依赖上一采样 token 的 Markov 特征，若做回溯式全局搜索，第 k 步的接纳决策会泄漏 x_{r,k}，破坏推测解码的无损性。论文在附录给出了具体反例。该贪心解为全局最优的前提是目标函数单峰，即硬件容量曲线平滑衰减；真实系统中 SPS 曲线非平滑、流水线异步，工程适配放在在线部署部分讨论。

1.4 训练目标

训练时从每条目标序列随机采样多个锚点位置构成 γ 长块，目标模型全程冻结，草稿模型共享其嵌入层与语言建模头且同样冻结，只更新骨干、串行块与置信度头。损失由三项加权组成：交叉熵 L_ce、分布匹配 L_tv（总变差距离，直接代理接受率）、置信度二元交叉熵 L_conf，权重分别为 0.1、0.9、1.0。三项都按 w_k = exp(−(k−1)/γ) 做位置加权，让更靠前、对前缀存活贡献更大的位置获得更高权重。

二、实验：离线接受长度与在线服务吞吐

离线实验刻意关闭置信度调度器，强制所有草稿器提出固定长度块，以隔离草稿质量本身；调度器的效果留到在线生产流量中检验。

仅有排序能力还不够。阈值式方法只需要置信度能正确排序草稿质量，而调度器要计算期望接受长度 τ，必须让累积存活概率的绝对幅度可信。神经置信度估计通常过度自信，因此 DSpark 引入顺序温度缩放：利用留出验证集，从左到右逐位置做一维网格搜索，在固定已校准前缀分数的前提下最小化累积乘积的期望校准误差。温度缩放是保序变换，校准概率幅度的同时不破坏置信度头学到的相对排序。

1.3 硬件感知前缀调度器

主结果如下表，数值为每轮接受长度 τ。

DSpark 在全部目标模型与全部九个基准上均取得最高接受长度。相对最强的并行基线 DFlash，Qwen3-4B/8B/14B 上宏平均提升 16.3%、18.4%、18.3%；相对自回归基线 Eagle3 提升 30.9%、26.7%、30.0%。绝对变化同样明显：Qwen3-4B 的 GSM8K 从 DFlash 的 5.40 升到 6.11，MT-Bench 从 3.07 升到 3.64。Gemma4-12B 上优势保持但幅度收窄，且出现一个例外：在 GSM8K 上 Eagle3 的 5.87 高于 DFlash 的 5.45，DSpark 的 6.05 只是小幅领先 Eagle3，说明跨模型家族时并行草稿的初始容量优势并不总成立。

表中还暴露出一致的领域效应：结构化任务接受长度天然更高，开放聊天最低。Qwen3-4B 上 DSpark 在数学与代码分别为 5.57 与 5.12，聊天只有 3.49。这正是固定长度验证会浪费算力的直接证据，也是置信度调度的动机。

2.1 逐位置条件接受率：并行为何能赢自回归

一个反直觉的现象是并行草稿器整体上常优于全自回归草稿器。论文用逐位置条件接受率解释：评估第 k 位时，分母只统计前 k−1 位全部被接受的实例，从而剥离前缀错误的惩罚，单独看该位置的预测质量。

结论是两种结构各占一段。第 1 位双方都只看目标上下文，差距来自架构容量：Eagle3 受 O(γ) 延迟约束只能用浅网络，而 O(1) 的并行草稿器可以用更深网络，于是 DFlash 在数学上以 0.88 对 0.81、聊天上以 0.72 对 0.53 领先。由于推测解码是严格前缀存活过程，第 1 位被拒就整块作废，初始容量优势被放大。到了第 2 至 7 位，Eagle3 的条件接受率保持稳定甚至上升（聊天从 0.53 升到 0.74），DFlash 则快速衰减（代码 0.87 降到 0.78，聊天 0.72 降到 0.63）。DSpark 继承并行骨干的高起点（数学 0.93），又靠串行头压住衰减，整块维持高而稳定的条件接受率。

2.2 深度、块长与延迟开销

固定块大小为 7、把 DSpark 层数从 1 扫到 5，接受长度随深度单调提升，最大边际增益出现在 1 层到 2 层之间；关键结果是 2 层 DSpark 在数学、代码、聊天三个领域都超过 5 层 DFlash。这说明用轻量串行头注入局部自回归，比单纯堆叠并行层更划算。

固定 5 层、把提议长度扫过 {4, 8, 12, 16}，DSpark 在每个长度上都优于 DFlash，且差距随块长扩大：γ=7 时数学、代码、聊天分别提升 16%、15%、18%，γ=15 时扩大到 30%、26%、22%。原因是纯并行草稿的边际收益随块长递减，而 DSpark 抑制了衰减。RNN 头相对 Markov 头只有边际增益，主要出现在更长块上，考虑到实现复杂度与部署属性，论文默认采用 Markov 头。

延迟方面，在批大小 128、上下文长度取 {512, 1024, 2048, 4096} 的算术平均下，一轮延迟包含一次目标验证、一次并行草稿前向与串行采样循环。由于该批大小下验证计算由目标模型主导，串行块开销可忽略：草稿长度从 4 增到 16，整轮延迟相对 DFlash 只增加 0.2% 到 1.3%，却换来最高 30% 的接受长度提升。

2.3 置信度头的离线诊断

在 Qwen3-4B 上做静态阈值扫描，阈值 0 对应标准固定长度验证。随阈值升高，整体接受率上升，因为置信度头剪掉了最终会被拒绝的 token。剪枝效果在聊天上最显著，接受率从 45.7% 升到 95.7%；数学从 76.9% 升到 92.5%，代码从 67.6% 升到 92.0%，结构化任务保留的草稿 token 更多。这验证了置信度头的判别能力，但静态阈值忽略系统负载，因此只作为诊断，真正的调度留给在线评估。

校准方面，Alpaca 数据集上的可靠性图显示原始置信度估计判别力强但系统性过度自信，后校准能把前缀存活概率与经验接受率对齐。这是调度器能用概率绝对值估算 τ 的前提。

2.4 在线部署

在 DeepSeek-V4 生产系统中，相比 MTP-1，DSpark 在匹配聚合吞吐下把单用户生成速度提升 60%–85%（V4-Flash）与 57%–78%（V4-Pro）。在严格 SLA 下（Flash 120 TPS、Pro 50 TPS），基线容量严重退化，DSpark 通过削减验证开销维持稳健吞吐，把此前不可达的交互性档位变为可用，外移了服务系统的帕累托前沿。需要指出，在线部分只报告了相对基线的速度与吞吐区间，未给出绝对硬件配置与请求分布，跨系统迁移时这些数字不能直接照搬。

三、总结

DSpark 的机制可以概括为两条互补的“预算再分配”：在草稿侧，把计算密集的部分留在并行骨干，只用轻量串行头（Markov 低秩转移或 RNN 门控）补上块内依赖，从而在草稿延迟近似与块长无关的前提下缓解后缀接受率衰减；在验证侧，用置信度头估计条件下接受概率、用顺序温度缩放校准累积存活概率，再由硬件感知调度器按全局吞吐最大化贪心选择每个请求的验证前缀长度，并用提前停止保证非预期性。

实验证据是分层的：离线在四个目标模型、九个基准上全部领先，Qwen3 三个规模上相对 DFlash 宏平均提升 16.3%–18.4%、相对 Eagle3 提升 26.7%–30.9%；逐位置分析说明增益来自“第 1 位的高容量加后续位的低衰减”；2 层 DSpark 超过 5 层 DFlash，串行头带来的整轮延迟开销仅 0.2%–1.3%；在线相比 MTP-1 在匹配吞吐下提升单用户速度 57%–85%。

边界同样清楚。贪心调度取得全局最优依赖目标函数单峰、即硬件容量曲线平滑衰减的假设，真实引擎的非平滑 SPS 与异步流水线需要额外工程适配；Gemma4-12B 的 GSM8K 上 Eagle3 反超 DFlash，说明跨模型家族时结论并非无条件成立；训练超参数与硬件细节未披露，离线结论也不能直接外推为任意并发下的在线收益。

可迁移的设计启示是：当系统里同时存在“质量”和“预算”两个可调维度时，不要把它们各自固定成超参数，而应让质量估计（校准后的置信度）去驱动预算分配（按负载变化的验证长度）。这一思路不限于推测解码，任何需要在多请求间分配有限批处理容量的推理服务都可以借用同一套“先估存活概率、再按吞吐曲线贪心接纳”的框架。
