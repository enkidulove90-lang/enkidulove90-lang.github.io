检索粒度该由谁决定？拆解 MixRAGRec 的三智能体 KG-RAG 推荐

发表于2026-05-27|更新于2026-05-29|推荐系统知识图谱
|总字数:3.2k|阅读时长:9分钟|浏览量:

论文：arXiv 2605.28175 · 代码：GitHub

检索不是越多越好

用 LLM 做推荐时，大家很容易把知识图谱检索当成一个”越多越好”的部件：既然模型缺事实知识，那就把相关的三元组、子图都塞进 prompt。

但真实查询的难度分布很宽。有的查询只需要一句常识就能答，有的则必须沿着多跳关系走一段图才能凑齐证据。同一个检索粒度套在所有查询上，两头都会出问题：对简单查询是过度检索——塞进去的无关三元组变成噪声，还白烧 token；对复杂查询是欠检索——证据不足，模型只能靠参数记忆去猜。

图 1：(a) 现有 RAGRec 对所有查询用同一检索粒度，要么被噪声拖累、要么知识不足；(b) MixRAGRec 按查询复杂度路由到合适的粒度，在”效用—成本”之间取平衡。

这篇论文的出发点就是这句话：检索粒度不该是一个事先拍定的超参数，而应该是一个针对每个查询做的决策。 围绕这个想法，作者搭了 MixRAGRec——一个三智能体协作的 KG-RAG 推荐框架。

三个 Agent 的分工

图 2：三个智能体各管一段——检索、对齐、推荐，最后由 MMAPO 在统一目标下联合优化。

整条流水线可以拆成三段，每段对应一个智能体：

  1. 混合专家检索 Agent：拿到用户查询后，从四个粒度不同的检索专家里选一个，从知识图谱里取回结构化知识；
  2. 知识偏好对齐 Agent：把检索到的三元组/子图，翻译成 LLM 能直接消化的自然语言片段；
  3. 对比学习增强的推荐 Agent：结合查询和对齐后的知识，产出推荐结果。

难点不在三个模块本身，而在”谁来监督检索 Agent”。检索动作的后果要经过对齐、再经过推荐才会体现在最终指标上——中间隔着两步。这个延迟依赖是整篇论文真正的技术核心，后面会专门讲。

四个检索专家：从”不检索”到”连通子图”

图 3：左侧是 KG 的构建与双索引，右侧是四个粒度递增的检索专家。

四个专家的粒度是刻意拉开的，覆盖”完全不需要外部知识”到”需要全局一致的知识”这一整段：

专家 粒度 做什么
Expert 1 DirectGenerator 不检索 直接返回空集，靠模型自身知识回答
Expert 2 TripleRetriever 三元组级 按语义相似度取 Top-M 个三元组，适合精确事实
Expert 3 SubgraphRetriever k 跳邻域 先选种子实体，再向外扩 k 跳，捕捉多跳关系
Expert 4 ConnectedGraphRetriever 连通子图 种子 + Personalized PageRank 选出重要实体，再取诱导子图

为了让这些检索能用同一套向量空间做，作者做了双索引：用同一个预训练语言编码器，把实体描述编码成向量建成实体库，把三元组（头、关系、尾三段文本拼接后）编码成向量建成三元组库。这样”查询—实体”和”查询—三元组”的相似度就在同一个空间里可比。

为什么最后一个专家要用最小生成树

Expert 4 是四个里最有意思的一个。PPR 选出重要实体之后，直接取诱导子图会带进来一堆无关边——实体是重要的，但连接它们的边未必和当前查询有关。

作者的处理是：把每条边的代价定义为查询与该边关系类型的语义距离，即 cost(e) = 1 - cos(z_q, z_r(e))，然后在这张子图上跑 Kruskal 算法求最小代价生成树。Kruskal 会按代价从小到大贪心地加边并避免成环，于是”用最贴合查询的关系，把重要实体连成一棵连通树”就成了一个可以被精确求解的问题。

这一步是整篇论文里最”干净”的设计：它没有引入新参数，只是把”什么叫相关的子图”翻译成一个可计算的目标函数。对做图检索的人来说，这种”把语义判断题改写成图优化题”的思路，比具体的公式更有迁移价值。

对齐 Agent：把图结构变成 LLM 能读的文本

图结构的知识不能直接喂给 LLM，而朴素地序列化（把三元组一行行拼起来）会同时带来两个损失：引入噪声（无关三元组混进上下文）和丢失结构（原本的图关系被拍平成文本）。

MixRAGRec 走的是”两步走”：

  1. 模板化：用关系感知的模板把每个三元组转成一句短陈述（”{头实体} 具有 {关系} {尾实体}”），图检索的结果则被线性化成一组关键关系陈述——这样不同粒度检索出来的结果，到了这一步有统一的输入格式；
  2. 对齐：对齐 Agent 再以查询为条件，把这份草稿精炼成一段”对下游推荐最有用”的知识片段。

对齐这一步在消融实验里是掉点最多的模块，尤其是 LastFM-1K 这种图谱关系类型特别多的数据集（312 种关系）。这其实说明一件事：在 KG-RAG 里，如何把知识”说给模型听”，和知识本身检索得准不准同样重要。 检索得再准，如果表达方式让模型无法利用，收益照样拿不到。

对比偏好反馈：为什么要专挑难负样本

推荐的正确标签只有一个，但”看起来也合理”的候选往往一大堆——同类型、同演员、同标签的条目，对模型来说都像是正确答案。不加区分地训练，模型很难把真正的目标项从这些强竞争项里分出来。

作者引入的策略是：

  • 用当前策略挑出概率最高的 Top-N 个错误候选，构成难负样本集；
  • 构造偏好对 (查询+对齐知识, 目标项, 难负样本)，用带参考策略的 log 比值损失来训练。

这个损失函数的形式和 DPO 同类：让当前策略相对于参考策略，对目标项的概率提升要显著大于对难负样本的概率提升。引入参考策略的作用是稳定训练——没有这个锚点，策略容易在偏好优化里跑偏。

关键在于**难负样本是”当前策略认为最难的”**，而不是随机采样或固定的相似度阈值。负样本会随着策略变强而变难，模型的判别边界因此被持续推向更精细的位置。

MMAPO：把”选哪个专家”变成一个动作来学

回到最核心的问题：检索 Agent 选哪个专家，怎么训练？

直接拿最终指标做监督是行不通的——检索这一步和最终结果之间隔着对齐、推荐两步，中间的延迟依赖让梯度很难正确地归因到”选专家”这个动作上。作者的解法是把整条流水线展开成一条轨迹，检索动作和对齐阶段的 token 生成都被看作不同时间步上的动作，然后：

  • 用稀疏的终局奖励（中间步骤奖励为 0，只有最后一步拿到总奖励）；
  • 给检索 Agent 和 对齐 Agent 各配一个价值基线，用 TD 残差 + GAE 估计优势。

这样，下游的奖励就能通过各自的价值基线，反向传导回”这一步该选哪个专家”的决策上。这一步是整篇论文能成立的前提：没有它，检索粒度就只能靠固定偏好或启发式规则来选——而消融实验里”随机选专家”和”去掉 MMAPO”都明确掉点，正好印证了这一点。

奖励设计：信息增益（KL）与检索成本的权衡

MMAPO 的奖励由两部分组成：

  • 推荐奖励 R_rec：推荐对了就给模型对该项的置信度，错了给一个固定小惩罚；
  • 边际信息增益奖励 R_MIG：用”这次检索带来的推荐分布变化”衡量知识价值——分布偏移越大，说明检索确实改变了模型判断，增益越高；再减去这次检索的计算成本（粒度越重成本越高）。

这里有个值得注意的细节：信息增益是用 KL 散度来度量的，基准分布取的是”不做检索”时的分布。把这两个式子放在一起看，它想表达的是一个很朴素的工程直觉——只有当检索带来的判断改变足够大、大到能覆盖它的成本时，才值得做这次昂贵的检索。

这也是全文最不”花哨”、却最实用的一处设计：它没有试图让模型学会”该检索多少”，而是给了模型一个明确的记账方式——收益要能报销成本。

实验说明了什么

作者在三个公开数据集上做了评测，知识图谱统一从 DBpedia 构建：

数据集 用户 物品 交互数 图谱实体 关系类型 三元组
MovieLens-1M 6,040 3,883 1,000,209 24,840 168 64,688
MovieLens-20M 138,287 27,278 20,000,263 72,673 223 272,173
LastFM-1K 992 107,528 19,150,868 180,457 312 516,604

在 LLaMA3-8B 和 Mistral-7B 两个开源骨干上，MixRAGRec 相对最强基线分别取得约 5.8%–20.4% 和 5.3%–18.3% 的相对提升；同时 Recall@K 也有改善，说明提升不只是把排序顶部挤了挤，而是整体质量在变好。

消融实验给出的信息量更大：

  • 去掉对齐模块掉点最多，尤其在关系类型最多的 LastFM-1K 上——知识”怎么表达”是瓶颈，不是附赠品；
  • 去掉难负样本采样或对比偏好反馈，准确率和 Recall@K 都稳定下滑；
  • 把专家选择换成随机、或去掉 MMAPO，结果都次优——路由必须被训练信号直接监督，不能靠启发式；
  • 检索预算对效果敏感：预算太小漏知识，太大引噪声，而且准确率最优与召回率最优对应的预算并不一致——这意味着预算不是”调大就好”，而是要按数据集与图谱规模去定。

三个可以抄走的点

  1. **把”超参数”改成”动作”**。检索粒度、检索条数这类量，过去是靠离线网格搜索拍定的；一旦把它建模成动作、用终局指标做信用分配，它就能随查询自适应。这个套路不限于 KG-RAG。
  2. 给收益和成本建一本账。用 KL 度量”这次检索改变了多少判断”，再减去计算成本——比让模型自己隐式学会”该检索多少”更可控、也更容易调试。
  3. 粒度必须和决策粒度匹配。这四个专家的粒度是显式设计出来的（不检索 / 三元组 / k 跳 / 连通子图），路由也在这个粒度上做决策。如果路由粒度比实际决策粒度更粗或更细，学到的策略和最终收益之间就会错位，收益会被抵消掉。

总结

MixRAGRec 值得看的地方不在于”用了 LLM + 知识图谱”，而在于它把三个原本各管一段的模块，用一套带成本意识的共享奖励串成了一个可训练的决策流程：检索粒度由查询决定，知识经过对齐才进入上下文，推荐用难负样本拉开区分度，而这一切都由 MMAPO 在统一目标下协调。

如果你在做 KG 检索增强的推荐，最值得先复现的是它的检索预算与专家粒度的对应关系，以及对齐模块的消融——这两个地方最能看出收益是从哪来的。
