Agent 范式与 Workflow 选择指南：什么时候用流程，什么时候才需要 Agent？

Agent 范式与 Workflow 选择指南：什么时候用流程，什么时候才需要 Agent？

最近很多 LLM 应用都会被叫成 Agent，但这个叫法其实很容易扩大化。一个能回答问题的聊天机器人、一次性的模型调用、一个情感分类器，都可以使用大模型，却不一定是 Agent。更重要的问题不是“有没有 LLM”，而是：模型是否在控制一个持续运行的工作流，是否会根据上下文选择工具，是否能判断下一步和退出条件。

这篇文章基于 OpenAI 的 A practical guide to building agents，把 Agent 的定义、三要素、工具类型、常见范式，以及多个业务场景里的架构选择整理成一份更偏工程落地的判断指南。

引言：为什么不是所有 LLM 应用都叫 Agent

如果系统只是把用户输入发给模型，再把模型输出展示给用户，它更像普通 LLM 应用。它可以很有用，但它不一定拥有“代理用户完成任务”的能力。

判断一个系统是不是 Agent，关键看模型是否参与管理工作流：它是否决定查什么、做什么、什么时候追问用户、什么时候调用工具、什么时候停止。

因此，Agent 不是为了炫技。它适合解决传统自动化难处理的问题：不确定性高、上下文复杂、数据非结构化、规则难维护、需要动态决策或多步工具调用。

OpenAI 对 Agent 的定义

OpenAI 对 Agent 的定义很克制：Agent 是能够代表用户完成任务的系统，它使用 LLM 管理工作流、做决策、判断任务是否完成，并在需要时调用外部工具或把控制权交还给用户。

这意味着简单 chatbot、单轮 LLM 调用、情感分类器、摘要器等系统，即使使用了 LLM，也不自动等于 Agent。只有当模型开始控制任务推进过程时，它才进入 Agent 的范畴。

Agent 的三要素

组成作用工程含义
Model负责推理、判断、计划和生成决定当前任务需要哪些步骤、哪些工具、何时停止
Tools获取信息或执行动作连接数据库、CRM、搜索、文档、邮件、审批、工单等系统
Instructions约束行为和边界定义流程、政策、权限、guardrails、人工升级条件和输出格式

Model

Model 是 Agent 的推理核心。它不只是生成文本，而是判断任务状态、拆解步骤、选择工具、解释工具结果，并决定是否继续执行。

Tools

Tools 是 Agent 连接外部世界的接口。没有工具的 Agent 很容易退化成“会说话但不能做事”的聊天应用。

Instructions

Instructions 决定 Agent 的行为边界。对于生产系统来说，指令不只是提示词，还包括权限、审批、失败阈值、人工介入和合规要求。

Tools 的三类

类型用途例子
Data tools获取上下文和信息查询 CRM、读取 PDF、检索知识库、搜索网页、查交易记录
Action tools执行真实动作发送邮件、创建工单、更新数据库、发起退款、转人工
Orchestration tools / agents-as-tools把其他 Agent 当作工具调度研究 Agent、写作 Agent、退款 Agent、安全审查 Agent

工具越接近真实业务动作，风险越高，越需要权限控制和人工确认。例如取消订单、授权大额退款、付款、冻结账户这类动作，不应该在没有 guardrails 的情况下完全自动化。

Workflow vs Agent 的核心区别

问题更适合 Workflow更适合 Agent
流程是否固定步骤清晰、分支可枚举路径会根据中间结果动态变化
规则是否稳定规则明确、更新频率低例外多，规则树持续膨胀
数据形态结构化字段为主文档、图片、对话、邮件等非结构化信息较多
动作风险低风险动作可自动执行高风险动作需要模型判断和人工确认
可测试性可用固定输入输出验证需要评估、轨迹、证据和失败阈值

一个实用原则是：能用规则稳定表达的，优先用 Workflow；只有当规则难维护、上下文复杂、任务需要动态展开时，再引入 Agent。

常见范式

Chatbot / RAG

适合 FAQ、知识库问答、产品文档助手。核心是理解问题、检索资料、基于文档回答。它不需要自主控制复杂工作流。

Workflow

适合固定步骤和固定审批流，例如差旅报销、请假审批、采购申请。LLM 可以辅助抽取字段或生成说明，但不必控制全流程。

Routing workflow

适合先分类再进入不同流程的场景，例如银行客服工单分流、售后类型判断、保险工单分类。

Parallelization

适合多维度独立检查，例如合同的法务、财务、隐私、安全、交付 SLA 并行审查。

Orchestrator-workers

适合子任务不可预判但需要中心汇总的任务，例如并购尽调、复杂研究、企业诊断报告。

Evaluator-optimizer

适合反复生成、检查和改进的任务，例如医药合规文案、法律文件润色、投标书优化。

Single Agent

适合多步工具调用和动态决策，例如电商退款、保险理赔、客户服务自动处理。

Multi-Agent

适合单 Agent 工具过载、规则混乱、领域边界明显的复杂系统，例如采购到付款、供应链风控、企业级财务运营。

Manager Pattern

适合需要统一入口和汇总的场景。用户只面对一个 Manager Agent，背后由多个专家 Agent 完成分析。

Decentralized Handoff

适合专家接管会话的服务系统，例如在线教育学生服务、医院患者服务、复杂客服中心。

业务场景选择表

业务场景推荐方案判断标准
FAQ、知识库问答Chatbot / RAG核心是查资料并回答，不需要自主执行动作
固定审批流Workflow路径清晰，规则可枚举
固定类别分流Routing workflow先分类，再进入对应流程
多维度独立检查Parallelization多个检查维度可并行执行
子任务不可预判但需要中心汇总Orchestrator-workers需要根据中间发现动态拆任务
反复生成-检查-改进Evaluator-optimizer有明确评价标准，需要多轮优化
多步工具调用和动态决策Single Agent需要模型查、判、做，并持续运行到退出条件
单 Agent 复杂到工具过载Multi-Agent工具、权限、领域、规则明显分化
统一入口和汇总Manager Pattern用户只想面对一个助手
专家接管会话Decentralized Handoff进入某领域后需要专业 Agent 多轮处理

具体案例

电商售后退款

售后退款需要查询订单、物流、商品信息、退款政策、用户历史记录和图片证据。小额、证据充分的请求可以自动处理；高金额、多次退款或证据不足时必须转人工。它适合 Single Agent，因为下一步经常取决于用户补充信息和工具返回结果。

保险理赔初审

理赔材料通常包括事故描述、照片、维修报价、警方报告、医院证明和保单条款。Agent 可以判断是否缺材料、是否在保障范围内、是否有矛盾证据，但不能直接承诺最终赔付。

供应商安全审查

供应商安全审查要读 SOC 2、ISO 27001、DPA、渗透测试报告和安全问卷。不同数据敏感度、访问权限、地区和业务关键性会改变审查路径，适合 Manager Pattern 或 Multi-Agent。

合同审查

合同审查可以用并行专家模式：法务看责任和赔偿，财务看付款和税务，隐私团队看数据处理，交付团队看 SLA。最后由 Manager 汇总风险、红线条款和建议替代文本。

客户成功续约风险分析

CSM Copilot 需要分析产品使用、支持工单、合同续约、NPS、会议纪要和扩展机会。用户体验上最好只有一个入口，背后调用多个专家 Agent。

金融反欺诈

欺诈判断不能只靠固定规则，需要结合交易历史、设备、地理位置、行为模式和异常上下文。Agent 可以生成调查报告，但冻结账户、拒付等动作必须有人工或规则保护。

企业采购到付款

Procure-to-Pay 涉及供应商准入、合同、预算、PO、收货、发票、税务和付款。单 Agent 工具过多时，应该拆成多个专业 Agent，由采购或财务 Manager 统一协调。

医药合规营销材料审查

医药文案需要医学准确、法规合规、引用完整、不能夸大疗效。适合 Evaluator-optimizer：生成初稿后，由医学、法规、品牌和引用检查器反复评估和修正。

内部 IT 支持

如果只是回答 VPN、邮箱、权限申请等问题，RAG 就足够；如果要查账号状态、重置权限、创建工单和升级人工，就进入 workflow 或 agent。

在线教育学生服务

学生可能从退款转到课程推荐，再转到就业指导。不同专家需要长期接管多轮对话时，Decentralized Handoff 更自然，但必须防止来回转交。

总结口诀

只是问答 → Chatbot / RAG
步骤固定 → Workflow
先分类再处理 → Routing
多角度同时看 → Parallelization
任务会动态展开 → Orchestrator-workers
需要反复打磨 → Evaluator-optimizer
要自己查、判、做 → Single Agent
一个 Agent 管不住了 → Multi-Agent
要统一用户体验 → Manager
要专家接管对话 → Handoff

最稳妥的落地方式是从小开始：先用真实用户验证简单流程，再逐步增加工具、评估、guardrails 和人工介入机制。Agent 的目标不是替代所有 workflow，而是在 workflow 无法可靠覆盖复杂上下文时，成为更灵活的控制层。
